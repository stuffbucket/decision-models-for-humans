# Contributing

## Add understanding, not volume

A contribution should do at least one of these:

- make a bounded judgment easier to picture;
- connect a model output to visible application behavior;
- add a distinct, runnable pattern;
- replace a claim with stronger evidence;
- document a failure or limitation;
- correct a provider or model fact from a primary source.

A long list of unverified links belongs in one of the broader directories listed in [RESOURCES.md](RESOURCES.md).

## Examples

Every example states:

- the user's job;
- the exact state available to the model;
- each question and allowed answer;
- how code maps answers to outcomes;
- whether outputs are invented, recorded, checked or evaluated;
- model and runtime identity;
- known failure cases;
- data provenance and license.

Do not submit private data, credentials, model weights without redistribution rights, or examples that identify a private person.

## Model entries

Use primary sources for identity, interface, license, price and provider claims. Record the date checked. Describe vendor benchmarks as vendor-reported. Do not rank models whose tasks or evaluation protocols differ.

A model name alone is not enough. Link the exact model card or API documentation and distinguish a moving alias from a pinned revision.

## Writing

- Start with a moment a reader can picture.
- Prefer “pick one,” “yes or no” and “pick a level” before provider vocabulary.
- Keep model judgment separate from application policy.
- State what a number does and does not establish.
- Include null, mixed, ambiguous and wrong cases.
- Do not use the System 1 analogy as a claim about machine cognition.

## Changes

Keep changes focused. Check links, spelling, Markdown rendering and whitespace before opening a pull request. Explain any user-visible change and the evidence behind changed factual claims.
